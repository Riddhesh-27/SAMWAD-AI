1. PROBLEM 1: MODEL RESPONSE IS SLOW (HIGH RECOGNITION LATENCY)
--------------------------------------------------------------------------------

[A] Root Cause Analysis:
  1. Frontend Network Request Throttling:
     - In `frontend/src/components/WebcamView.jsx`, each frame capture is scheduled
       with `animationFrameId = setTimeout(processFrame, 160)` inside the `finally` 
       block AFTER waiting for the network response.
     - With image encoding and network turnaround taking ~140-160ms, each frame cycle 
       takes 300-320ms, producing only ~3.1 frames per second.
  2. Image Encoding & Payload Size:
     - The client captures a 320x240 canvas and encodes it as a base64 JPEG at 0.65 quality.
     - The backend must decode the base64 string, run OpenCV `imdecode`, perform BGR->RGB 
       conversion, and create an `mp.Image` wrapper before detection can even begin.
  3. Excessive Temporal Stabilizer Buffer Lag:
     - In `backend/app/services/stabilizer.py`, `window_size = 6` with `stability_threshold = 0.65`.
     - At ~3.1 FPS, collecting 6 consecutive frames requires:
       6 frames * 310 ms = ~1.86 SECONDS of holding the hand completely frozen!
     - In a live demo, waiting ~2 seconds for a sign to register feels unresponsive, 
       laggy, or frozen.

[B] Proposed Solution & Exact Changes:
  1. Optimize Client-Side Frame Capture (`WebcamView.jsx`):
     - Reduce offscreen resolution to 256x192 with JPEG quality 0.50 (MediaPipe HandLandmarker 
       internally processes 224x224 / 256x256, so higher resolution only adds CPU encode/decode waste).
     - Reduce the throttle delay from 160ms down to 40-50ms.
     - This increases effective capture rate from ~3 FPS to ~10-12 FPS.
  2. Optimize Prediction Stabilizer Parameters (`stabilizer.py`):
     - Reduce `window_size` from 6 down to 3 or 4 frames.
     - Adjust `stability_threshold` to 0.66 (meaning 2 out of 3 or 3 out of 4 matching frames 
       will immediately confirm the sign).
     - At 10 FPS, confirmation time drops from ~1.86 seconds down to ~250–350 milliseconds!
     - The model will respond virtually instantaneously while maintaining stability against jitter.

2. PROBLEM 2: REPEATED WORD ACCUMULATION ("WELL DONE WELL DONE", "LIKE LIKE")
--------------------------------------------------------------------------------

[A] Root Cause Analysis:
  1. Stabilizer Cooldown Timeout Reset:
     - In `backend/app/services/stabilizer.py`, `cooldown_seconds = 1.2`.
     - When a user shows "WELL DONE" or "HELLO" and keeps their hand in frame for 2.5 seconds, 
       the cooldown expires after 1.2s and the stabilizer triggers AGAIN, appending the 
       identical sign a second time into the buffer: "WELL DONE WELL DONE".
  2. Unconditional Append in Frontend:
     - In `frontend/src/App.jsx`, `handleSignRecognized` appends every recognized event 
       without checking if it is identical to the preceding word/phrase.
  3. Grammar Refiner Does Not Deduplicate Repeated Words:
     - In `backend/app/services/grammar_service.py`, `refine()` lacks a deduplication pass.
     - For repeated multi-word phrases like "WELL DONE WELL DONE", the gloss pattern matches 
       only the first occurrence (`count=1`), producing distorted outputs like 
       "Well done! Excellent work. WELL DONE".
     - Similarly, repeated words like "LIKE LIKE" or "PLEASE PLEASE" remain untouched.

[B] Proposed Solution & Exact Changes:
  1. Add Comprehensive Deduplication to Grammar Engine (`grammar_service.py`):
     - Implement a pre-processing deduplication function:
       * Multi-word phrases deduplication: e.g. "WELL DONE WELL DONE" -> "WELL DONE",
         "THUMBS UP THUMBS UP" -> "THUMBS UP", "I LOVE YOU I LOVE YOU" -> "I LOVE YOU".
       * Single word deduplication: collapses consecutive identical words 
         (e.g. "LIKE LIKE" -> "LIKE", "HELLO HELLO" -> "HELLO").
     - Add rule tracking to `rules_applied`: "Deduplicated repeated words/gestures".
  2. Implement Sustained Gesture Hold-Lock in Stabilizer (`stabilizer.py`):
     - When a gesture is confirmed and emitted, place it into a "Hold Lock" state.
     - It will NOT re-emit the same sign as long as the user continuously holds the hand 
       in that same pose.
     - To emit the same sign again, the user must either change gesture, lower their hand, 
       or reset, preventing unintended duplicate accumulation.
  3. Client-Side Buffer Guard (`App.jsx`):
     - Guard `handleSignRecognized` so it does not auto-append consecutive identical words 
       within a short time window.

3. PROBLEM 3: WORD SIGNS COLLIDING WITH ALPHABET LETTERS (A-Z)
--------------------------------------------------------------------------------

[A] Root Cause Analysis:
  1. Physical Geometry Overlap between ASL Alphabet and Conversational Gestures:
     - Letter "F" (thumb touching index tip, 3 fingers up) is IDENTICAL in hand shape 
       to the "OKAY / PERFECT" gesture 👌.
     - Letter "V" (index and middle fingers up in V shape) is IDENTICAL in hand shape 
       to the "PEACE / VICTORY" gesture ✌️.
     - Letter "Y" (thumb and pinky extended, middle fingers curled) is IDENTICAL in 
       hand shape to the "CALL ME" gesture 🤙.
     - Letter "D" / "1" (index pointing up, other fingers curled) is IDENTICAL in hand 
       shape to "YOU / POINTING" 👉.
     - Letter "B" (open hand, fingers upright) resembles "HELLO / OPEN PALM" 👋.
     - Letter "A" / "S" (closed fist) resembles "STOP / FIST" ✊ or "WELL DONE / THUMBS UP" 👍.
  2. Unconditional Hardcoded Precedence in `recognition.py`:
     - In `backend/app/routes/recognition.py`, lines 81-96:
       `conv_gesture = analyze_conversational_gesture(raw_landmarks)`
       `if conv_gesture and conv_gesture["confidence"] >= payload.threshold:`
       `    # Always return conversational word sign!`
       `else:`
       `    # Fall back to PyTorch alphabet classifier`
     - Because conversational gestures take absolute precedence, the user can NEVER 
       type letters "F", "V", "Y", "B", "D", "A", or "S" because they are always 
       hijacked into "OKAY", "PEACE", "CALL ME", "HELLO", "YOU", "STOP", or "WELL DONE"!

[B] Proposed Solution & Exact Changes:
  1. Dedicated Recognition Mode Architecture:
     Provide 3 user-selectable recognition modes:
     - Mode 1: "Letters (A–Z)" [Fingerspelling Mode]:
       Bypasses conversational gesture heuristics completely. 
       Pure 26-letter PyTorch MLP neural network classification.
       Allows users to spell any word or name (e.g. "VICTORY", "FAMILY", "YELLOW") 
       without getting hijacked by word signs.
     - Mode 2: "Word Signs" [Conversational Mode]:
       Prioritizes conversational gestures (Well Done, Hello, Peace, Okay, I Love You, 
       Call Me, Pointing, Stop, Disagree).
     - Mode 3: "Smart Auto" [Hybrid Mode]:
       Smart disambiguation that evaluates both PyTorch classifier confidence and 
       geometric heuristics, applying stricter geometric criteria before overriding 
       an alphabet sign.
  2. Backend API Parameter (`FrameRecognitionRequest` & `LandmarkRecognitionRequest`):
     - Add `mode: str = "auto"` (accepting `"auto"`, `"letters"`, or `"words"`).
     - In `recognize_frame`, branch based on the selected mode:
       * If `mode == "letters"`: directly run `classifier.predict()` and ignore conversational heuristics.
       * If `mode == "words"`: prioritize conversational heuristics.
       * If `mode == "auto"`: apply intelligent disambiguation.
  3. Frontend Mode Switcher UI:
     - Add a clean, accessible 3-button mode toggle selector on the Live Vision Feed panel 
       above the camera or next to the Confidence Threshold:
       [ 🔤 Letters (A-Z) ]  [ 💬 Word Signs ]  [ ⚡ Smart Auto ]
     - Default to "Smart Auto" or "Letters (A-Z)" with instant switching.
     - Show current active mode badge on the video HUD.
